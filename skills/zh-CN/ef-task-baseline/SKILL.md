前置条件——本 Prompt 经我明确启用并创建 baseline 文件后，每轮我给出反馈，你都要根据本 Prompt 维护同一份任务基线文件。

## 0. 元规则

（本条约束第 1—6 条及其全部子条款本身如何被维护；在文件维护范围内优先于以下条款，但不改变更高层级指令的效力；本条自身也适用此规则。）

- 创建 baseline 文件时，在文件最顶部设置独立章节「书写规则」。
    
- 「书写规则」的范围固定为：从本 Prompt 的“0. 元规则”开始，到“6.4 遗漏兜底”结束的全部正文，包括本条自身及所有子条款；不包括“前置条件”说明、Prompt 外的解释、示例、讨论和版本变更说明。
    
- 创建 baseline 文件之后，只有我明确要求新增或修改书写规则时，才同步更新本章节；不得只修改聊天中的口头约定而不更新文件。
    
- 在文件维护范围内，「书写规则」章节默认不可变，不受第 5.5 条「作废与删除」机制约束。任何轮次的总结、压缩或精简均不得删减、改写、意译或省略本章节，只能整体保留当前版本的原文。
    
- 你不得依据自己的判断认定本章节“已过时”“不再需要”或“可以精简”，不得自行移除或改写。如确需修改本章节，只能由我直接下达明确指令。修改时必须：
    
    1. 更新规则版本号；
    2. 在变更记录中记录修改内容、原因和生效轮次；
    3. 将新版本完整写入本章节；
    4. 不得只修改聊天中的口头约定而不更新文件。
- 首次创建 baseline 并按第 1 条要求回显文件名和初始内容时，本章节内容必须完整包含在该次回显中，供我核对规则确实已写入。除首次创建或书写规则本身发生变更外，后续普通轮次不要求重复回显完整的「书写规则」章节，只需说明本轮规则是否发生变化。
    
- 本条不要求你对所有执行细节进行主动审计；但第 6 条要求的每轮结尾自评必须执行。该自评仅是回显内容，不写入基线文件，也不作为下一轮的事实依据。
    
- 本条要求你每轮结尾按第 6 条回显基线文件名和规则版本号，并给出执行自评。
    

## 1. 任务基线文件

- 以你刚刚输出的内容和我的说的话作为基准，在仓库根目录维护一份任务基线文件。文件名由你根据本次任务内容命名，格式为 `BASELINE_<任务简称>.md`。
    
- 创建后第一时间回显文件名和初始内容。后续所有轮次固定使用这一份文件，不得新建或改名。
    
- 本文件作为本任务唯一的任务基线文件。各章节的效力按第 3 条区分，不因内容被记录在本文件中，就自动成为执行依据。
    
- 本文件记录：
    
    - 初始目标：
        
        - 整个任务的目标；
        - 本阶段成功标准，单独标注适用阶段及确认状态，不得替代整个任务目标。
    - 不可变约束；
        
    - 当前有效方案；
        
    - 待确认项；
        
    - 简短变更记录；
        
    - 参考信息。
        
- 「当前有效方案」中的每个可独立确认、取消或核对的条目，必须使用稳定且唯一的编号，格式为 `S-001`、`S-002`，依次递增。
    
- 新增条目使用新编号；条目排序变化不得改变编号。仅纠正文字且不改变含义时保留编号；经用户确认、改变条目要求的替换使用新编号，并在变更记录中注明替代关系。
    
- 已取消或被替换的条目不再保留为当前有效条目，其编号及取消或替换关系记入变更记录，旧编号不得复用。执行确认与自评均引用当前有效编号。
    
- 本 Prompt 被用户明确启用后，方案讨论阶段仅允许创建和维护本任务唯一的 baseline 文件；这是对“方案阶段不修改文件”的限定例外，不授权修改业务代码或其他文件，也不构成执行授权。
    
- 文件内容记录整个任务目标，不得用某个阶段目标替代整个任务目标。
    
- 每轮处理反馈前，先读取当前 baseline 文件中的以下内容：
    
    - 规则版本号；
    - 当前有效方案；
    - 待确认项；
    - 最近的变更记录；
    - 根据本轮问题及其涉及的目标、方案条目、文件、组件或术语，在「参考信息」中查找并读取相关条目；不得仅因聊天上下文中不再出现某项信息，就视为该信息不存在。
- 在重新搜索、重复尝试或重新作出技术判断前，先检查基线是否已有相关结论及其适用条件。已作废条目不得作为当前事实；既有结论的适用条件与本轮不符或无法确认时，不得直接沿用，需进行必要核对。
    
- 普通轮次无需重复读取完整「书写规则」章节。只有发生以下情况时，才读取完整「书写规则」章节：
    
    1. 首次创建 baseline；
    2. 书写规则发生变更；
    3. 发现规则范围、条款编号或文件内容存在冲突；
    4. 上一轮遗漏了第 6 条规定的回显；
    5. 执行前需要核对维护规则。
- 处理反馈并完成必要的文件更新后，再输出第 6 条规定的回显。
    

## 2. 候选变更与确认

- 我的反馈默认只是候选变更。
- 只有我表示认可时，才将对应内容写入「当前有效方案」。
- 未点名的条目保持不变。
- 取消或替换必须明确标记。
- 未确认的候选变更只能记录在「待确认项」，不得写入「当前有效方案」。
- 用户确认后，才能将对应候选变更从「待确认项」转入「当前有效方案」。
- 不得从模糊表述中推断我已经确认整体方案。
- 仅在用户明确启用“本阶段成功标准未被反对即视为确认”的协作规则时，允许以下例外：助手提出的本阶段成功标准，先记为待确认；用户在下一轮继续推进该阶段且未提出异议时，标记为已确认，并在本轮回显中说明。
- 此例外仅适用于本阶段成功标准，不适用于任务范围、不可变约束、当前有效方案或执行授权。若成功标准涉及上述内容的新增或修改，涉及的部分仍须用户明确确认。
- 本阶段成功标准记录在「初始目标」下，不因其获得确认而自动写入或改动「当前有效方案」。

## 3. 变更记录与执行依据

- 文件中保留简短变更记录。执行时：
    
    - 「当前有效方案」限定已确认的实施内容与范围；
    - 「初始目标」及其中已确认的本阶段成功标准，用于判断任务结果是否合格；
    - 「不可变约束」限定实施和结果均不得突破的边界。
- 不得仅依据目标或成功标准，自行新增有效方案之外的实施内容。若有效方案不足以满足目标或成功标准，或与不可变约束冲突，停止执行，列出需要确认的方案变更。
    
- 「待确认项」「变更记录」「参考信息」不产生实施授权；不得从聊天中的中间讨论自行补充、覆盖或推断需求。用户的新指令按本 Prompt 的确认与维护流程同步到文件；发现聊天与文件冲突时，按第 4 条处理。
    
- 完成本轮反馈处理及第 5.2 条要求的信息筛选后，只有在有效方案、待确认项、目标及成功标准、约束、参考信息和其他按本 Prompt 应维护的内容均无需更新时，才可以不改变文件内容，并明确说明“本轮无文件变更”。不得仅以“本轮没有确认方案变更”或“本轮只有讨论”为由跳过应记录的信息。
    

## 4. 执行前确认

- 执行前回显「当前有效方案」，等待我确认后再执行。
- 如果聊天与文件冲突、文件存在歧义或疑似漏项，停止执行并列出冲突，让我决定，不得自行取舍。

## 5. 参考信息记录

本条仅新增文件中的「参考信息」章节，不改变第 1—4 条的任何效力。

### 5.1 位置与效力

- 基线文件中设置独立章节「参考信息」，与「当前有效方案」「待确认项」平级且物理隔离，不得混写，不得互相引用替代。
- 本章节不构成需求、不构成变更、不作为执行依据。
- 与「当前有效方案」冲突时，一律以后者为准。
- 发现冲突时，立即停止执行并报告，不得自行调和，不得据此推断我“其实想要”什么。

### 5.2 主动筛选与记录范围

每轮处理反馈时，你必须检查本轮对话、实际阅读的源码和实际检索的资料，识别尚未记录、且对本任务有明确用途的信息。此要求不意味着每轮必须额外搜索、读取无关文件或重复验证既有结论。

满足以下任一用途的信息，应在符合本条记录范围及第 5.3—5.4 条要求的前提下，主动写入「参考信息」，无需事先询问：

- 帮助判断目标是否可达、方案是否可行；
- 解释关键选择、限制或问题成因；
- 帮助后续实施、验证或定位问题；
- 避免遗忘已经获得的结论、重复尝试或重复排查。

可直接记录的范围：

1. 外部检索获得的相关事实、结论及适用条件；
2. 实际阅读源码确认的行为、接口、依赖关系和限制；
3. 我说过的偏好、工具链习惯；
4. 被否决的方案及否决理由；
5. 已知的环境、依赖和权限条件；
6. 本任务内的术语约定；
7. 实际进行的尝试、验证或排查，其结果，以及该结果能够排除或尚不能排除的方向；
8. 对话、源码或资料中形成的关键解释、因果分析与技术判断；其中未经验证的推断必须按第 5.3 条标记。

记录前必须说明该信息对本任务的具体用途；说不清用途的不记录。与已有条目含义相同、且没有新增证据或适用条件的信息，不重复记录；需要更正既有信息时，遵守第 5.5 条。

需求性内容仍按第 2 条处理，不得因符合上述用途而写入「参考信息」。白名单之外的信息不得自行记录，需用一句话询问我。

### 5.3 禁止记录

- 需求性内容：我在讨论中提出的想法、期望或“要不要加 X”，一律按照第 2 条作为候选变更处理，不得以“有用信息”的名义写入本章节。
- 不得根据我的行为归纳我的偏好。第 5.2 条第 3 项只允许记录我明确说过的偏好。
- 第 5.2 条范围内确需保留的推断，必须标记为「假设-需验证」，说明验证方式，以及若不成立会影响哪项判断，并在回显中单独点名。
- 「已读确认」只表示来源明确支持所记录的陈述，不自动证明来源中的技术判断正确。对话只能证明某人提出过某项说法时，应记录为“用户报告……”或“助手提出……”，不得改写成已验证的客观事实。
- 用户对方案的确认不等于对其中技术推断的验证。由一次尝试推导出的普遍结论、问题成因或排除结论，若证据不足，仍须标记为「假设-需验证」。
- 不记录大段原文或代码，只保留来源定位和一句话概括。

### 5.4 记录格式

缺少必要字段时不得写入，不得编造来源、行号、轮次或验证结果。

统一格式为：

```
[已读确认 | 假设-需验证] 来源定位 | 一句话概括及必要的适用条件 | 对本任务的用途 | 记录于第 N 轮
```

来源定位可使用：

- 源码：文件路径及行号；
- 外部资料：URL 或可定位的文档名、章节；
- 对话：第 N 轮、发言方及话题定位；
- 尝试或验证：第 N 轮、执行的命令或操作，以及关键结果摘要；已有日志或报告时附其位置。

「假设-需验证」条目还须补充：验证方式，以及若不成立会影响哪项判断。

只保存足以理解和追溯结论的信息，不复制大段对话、代码或日志。

### 5.5 作废与删除

- 信息过时必须标记作废，不得静默改写或覆盖：
    
    ```
    ~~原文~~ [已作废@第 N 轮] 原因一句话
    ```
    
- 作废条目下沉到「参考信息」章节末尾。
    
- 若某条信息存在误导执行的嫌疑，你可以提出删除建议，但必须说明“它具体会怎样误导执行”。
    
- 只有我确认后才能删除，不得先删后报。
    

### 5.6 回显义务

- 本条规定的参考信息回显统一按照第 6.1 条的 A 组输出，不在其他位置重复输出。
- 本轮无新增、修改或作废时，写“本轮无”。

## 6. 每轮回显义务

### 6.1 回显位置与结构

每轮回复结尾固定输出以下两组内容，物理分开、分别标注，不得混写为同一段：

**【A 组｜客观事实】**

可由我直接核对文件验证：

- 基线文件名 + 当前规则版本号；
- 本轮文件变更：列出变更内容；无变更则写“本轮无文件变更”；
- 本轮「参考信息」的新增、修改、作废条目；无变动则写“本轮无”。

**【B 组｜执行自评】**

仅表示你的主观判断，不是客观事实：

- 本轮执行是否偏离「当前有效方案」、任务目标、已确认的本阶段成功标准或不可变约束；
- 若标记为「未偏离」，列出本轮实际对照的有效方案条目编号，以及相关目标、成功标准和约束的定位。未涉及实施或验收时，明确说明，不以“未偏离”表示任务已经完成或验收通过。

使用用户能直接理解的中文，先说具体发生了什么，不堆术语，不只报章节名、条目编号或抽象结论。
A 组说明本轮具体记录、调整或作废了什么；涉及替换时，说清从什么改成什么。不得只写“已同步基线”“已更新参考信息”等无法看出内容的表述。
B 组保留第 6.2 条规定的状态标签和对照定位，并用简短人话说明本轮做了什么、是否符合已确认要求；引用编号时附上对应要求的简短含义，不要求用户翻文件才能理解。
必须使用技术术语时，在首次出现处简短说明它在本任务中的含义。无变更、无相关动作时直接说明，不为满足格式重复解释或凑字数。
易读表达不得省略原有必填信息，不得将推断说成事实，也不得把“未偏离”说成“已经完成”或“验证通过”。

### 6.2 自评规则

- 结论只能是以下三者之一，不得自由发挥：[未偏离] / [有偏离] / [无法判断]。
- 三种结论均属于状态报告，不构成处罚。标记为 [有偏离] 不应被规避或隐藏。
- 标记为 [未偏离] 时，必须按第 6.1 条列出实际对照项，不得只给结论。
- 标记为 [无法判断] 时，必须说明缺少哪些具体证据或信息；不得以“无法判断”代替本可通过读取 baseline 或核对文件获得的判断。
- 自评对照第 3 条规定的有效方案、目标、已确认的本阶段成功标准及不可变约束，不以「参考信息」产生额外要求。
- 自评结论只出现在回显中，不写入基线文件，不作为下一轮的事实依据。

### 6.3 有偏离时的处理

结论为 [有偏离] 时，立即停止执行，等待我处理，并说明：

- 偏离了哪一项有效方案、目标、已确认的本阶段成功标准或不可变约束，并给出对应定位；
- 具体哪个动作或产出与之不符；
- 为什么会偏离（推理偏见、信息缺失、看错或方案本身有歧义）。

不得自行修正后继续，不得先执行后报告。

### 6.4 遗漏兜底

- 某轮结尾未输出 A 组回显的，视为该轮未完成基线维护。
- 下一轮开始时，必须先读取当前 baseline 文件和上一轮对话，核对上一轮是否存在应记录但未记录的确认变更或参考信息。
- 在完成核对和必要的文件维护前，不得继续执行任务，也不得仅以“上轮无变更”为由跳过。
