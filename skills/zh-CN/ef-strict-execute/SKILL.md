按 `<PLAN_DOCUMENT_PATH>` 文档操作方案执行代码修改。

## 执行范围

- 执行【方案详解】/【改什么】中的 diff：(a) 必需和 (b) 安全/健壮性必需全部执行；(c) 可选优化跳过
- 方案未列出的文件、函数、行不要改动
- 【额外发现】【业务影响】【回归测试】【未修改声明】是参考信息，不是执行项
- 本轮实行单写者：不得启动多个子 Agent 并行生成、应用或修改 diff，也不得让子 Agent 同时改动当前工作区；全部代码修改由你按方案顺序完成

## 开工前

1. 执行 `git status` 并贴出结果。若工作区有未提交改动（未跟踪的文件除外），停下问我先 stash 还是继续
2. 读取【读取范围】列出的全部文件的当前内容
3. 核对每条 diff 与当前代码的对齐情况，分三种处理：
   - 上下文完全对齐 → 正常执行
   - 行号漂移但函数/锚点代码仍在 → 按锚点定位后执行，汇报时标注"锚点对齐执行"
   - 函数已不存在 / 关键代码已被改写 / 逻辑层面与方案描述矛盾 → 停止执行该条，记入"方案与现实冲突"清单，等我决定
4. 若方案中的 [假设] 项与实际代码不符，同样记入冲突清单，不要自行猜测应用

## 执行时

- 机械应用 diff，不做额外改写：不格式化、不补注释、不重构、不顺手修 bug
- 发现方案外的 bug 或隐患，记入"发现但未处理"清单，不要动手
- 编译 / 类型检查若失败：
  - 属于应用 diff 时的机械失误（import 遗漏、括号不配对、明显拼写）→ 允许自行修复，但必须在汇报中标注"自行修复"并列出修了什么
  - 属于方案本身的逻辑问题 → 不要修，如实贴出等我决定
- 全部代码修改完成后，彼此独立且不会改动已跟踪文件的验证命令可以并发运行；这不授权任何 Agent 自行修复方案逻辑或扩大 diff

## 完工汇报

1. 检查是否有已跟踪文件的未提交改动（未跟踪的新文件忽略）。若有，在汇报开头用一句话标注（例如"执行前已跟踪文件有未提交改动，涉及 X 个文件，本次 git diff 可能包含任务外内容"），然后继续执行。未跟踪文件不用管也不用汇报
2. git 改动：
   - `git diff --stat` 输出
   - 若有方案未列出的文件被动过，单独说明原因
   - 完整 diff 不用贴，我需要时会单独要
3. 未执行的 diff：编号 + 原因
4. 方案与现实冲突：列出方案描述与实际代码矛盾的地方，说清冲突点
5. 编译 / 类型检查结果：命令 + 输出。若有自行修复，单独列出
6. 自审（切换到代码审查者视角，重新读每处改动，逐条回答）：
   - 是否改变了函数原有的行为边界（入参范围、返回值、异常情况）？
   - 调用方是否需要同步调整？有没有遗漏的调用点？
   - 是否引入了新的依赖（包、全局状态、副作用）？
   - 这处改动在边界情况下（空值、并发、极端输入）是否仍然正确？
   - 发现疑点直接说，不要为了交差强行通过
7. 需要我手动确认的点：从方案的【回归测试清单】中，挑出本次改动实际触发的项目列出（方案列了但本次没改到的不用列）。说清操作和预期
8. 发现但未处理的问题：方案外注意到的 bug 或隐患
9. 未动区域：改动范围外的文件是否一行未改
