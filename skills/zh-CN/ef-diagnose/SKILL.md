——————————
定位与本问题相关的代码路径并充分阅读（说明你读了哪些文件、为什么认为它们相关、是否可能有遗漏）。
本轮禁止：修改/创建/删除任何文件、执行会改变项目状态的命令、在回复里贴出"建议的完整改动代码"。允许的输出只有：分析、结论、推理、以及引用现有代码作为证据。
基于实际代码给出答复，要求：
- 结论明确。若证据充分指向单一答案，直接给出；若存在多种可能性或依赖运行时条件，如实列出各分支及其触发条件，不要强行收敛
- 每个关键推理步骤给出证据定位：文件路径 + 行号 + 一句话概括该处代码做了什么，不要贴完整代码片段
- 区分"代码里确实这么写"和"我据此推断"，后者单独标注
- 若某处结论依赖你未读到的代码、未验证的假设、或外部配置/环境，明确说出来，不要脑补
- 若当前工具支持子 Agent，且存在至少两条互不依赖的代码路径或根因分支，则通过只读 子Agent并发分派只读取证；否则由你自行完成，不要为凑并发扩大阅读范围
- 每个 子Agent 只返回实际读取文件、文件:行号、事实/推断和未覆盖项；最终相关范围、根因分支与结论由你统一复核，决定性证据必须亲自打开确认
输出分两部分，顺序固定：

## 第一部分：结论（给不看代码的人读）

- 用 3~6 句话回答：什么情况下会出问题 → 用户/运维会看到什么现象 → 根因一句话 → 是否需要处理、影响范围多大
- 描述视角是"谁、做了什么操作、看到了什么变化"，不是"哪个函数、哪个字段"
- 本部分不出现文件路径、行号、函数名、变量名；必须出现的术语，紧跟一句话解释它在这里指什么
- 禁止比喻、类比
- 存在多个分支时，每个分支单独一句：在什么条件下 → 会看到什么
- 最好不要直接输出一大段话，必要时分类分点加粗之类的增加可读性。

## 第二部分：证据（给核对的人读）

- 读了哪些文件、为什么相关、可能遗漏什么
- 每个推理步骤：文件:行号 + 一句话概括，标注 [代码确认] 或 [推断]
- 未验证的假设及其不成立时结论如何变化

写完后自检：只看第一部分，一个不看代码的人能否回答"发生了什么、影响谁、要不要处理"。不能就重写第一部分。
