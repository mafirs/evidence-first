# dev-flow

质量是目标，流程是最低要求。下面每个阶段只规定"交付什么、怎样算通过"，怎么读代码、怎么想方案由你判断。某个关卡的要求和交付质量冲突时，选质量，并在汇报里写明你偏离了哪条、为什么。

`references/execution-rules.md` 里的执行层规则（阶段分离、最小修改、(a)/(b)/(c) 分类、安全规则、验证与汇报）照常适用，开工前读一遍。用户自己的全局规则或本次对话里的明确指令和它冲突时，以用户的为准；用户在本次对话里的明确指令优先于本技能。

## 入口

用户点名哪一段就只做哪一段。做完这一段就停，不自动进入下一段；汇报这一段产出了哪些文件、有哪些需要用户决定的点、要继续时可以怎么说（例如"dev-flow 接着执行 <运行目录>"）。用户没有点名某一段时走完整流程。

- **完整流程**：开工准备 → 阶段 0-10。
- **定位**：阶段 0、阶段 1（大改小改都做）。只读，不切分支。产出 `requirement.md`。
- **出方案**：阶段 0、阶段 1（只有大改）、阶段 2、阶段 3。只读，不切分支。产出 `requirement.md`、`plan.md`、`scope.txt`、方案评审记录和 `closed.md`。
- **执行**：用运行目录里的 `plan.md`；用户直接给了方案时，原样存成 `plan.md`，开头注明来源。运行目录里没有 `requirement.md` 时按阶段 0 写；没有 `scope.txt` 时按方案 diff 涉及的文件写。然后开工准备 → 阶段 4-7 → 把改动 commit 到功能分支。不做方案评审和独立评审，用户要求时再做。
- **评审方案**：评审运行目录里的 `plan.md`，或用户给的方案（原样存成 `plan.md`，开头注明来源）。缺 `requirement.md`、`scope.txt` 时同上补齐。跑阶段 3 的第 1 轮，按「处理评审意见」逐条判定，写进 `closed.md`。只评审，不改方案；用户说按评审意见改，再按阶段 2-3 改方案、做定向复审。
- **评审代码**：评审已 commit 的改动：运行目录里的功能分支，或用户指定的分支、commit 范围。先按下文「评审代码的准备」准备好，再跑阶段 8 的第 1 轮，逐条判定写进 `closed.md`。只评审，不改代码。
- **自检**：按阶段 7 跑一轮，只报告，不修。
- **处理评审意见**：见下文「处理外来评审意见」。只判定，不改代码或方案。
- **接着走**：用户给出运行目录，或给出任务简称（在 `~/.vibe-runs/<仓库名>/` 下找；找到多个就问用户）。按下文「判断做到哪一步」找到下一步，做到用户点名的那一段结束；没点名就走完完整流程。

### 判断做到哪一步

只看运行目录里的文件和仓库状态，不另外记进度：

- 有 `requirement.md`：阶段 0 已做。
- 有 `plan.md`：方案已写；有 `review-plan-<n>.md`：方案评审已跑到第 n 轮。
- 有 `base`，且 `branch` 记录的分支在 `base` 之后有 commit 或有未提交改动：已开始执行。`checks.log` 里有哪些检查、结果如何，决定阶段 6 是否已通过。
- `closed.md` 里有 self 开头的条目：fork 自检已跑。
- 有 `review-code-<n>.md`：独立评审已跑到第 n 轮。
- 有 `pr.md`：已完成。

文件之间对不上（例如 `plan.md` 比最后一轮方案评审时的快照新，却没有复审记录）时，在汇报开头写明你的判断和依据。

## 用户原话怎么用

用户原话是最终依据，但原话里不同的话分量不同：

- **决定**（做什么、不做什么、范围、限制）：照做。成功标准和不许做的事只从决定里来。
- **比方 / 理由**（例子、类比、解释和动机）：用来理解用户想要什么，不单独推出规则，也不能拿来压过证据。
- **事实判断**（用户对代码现状、问题原因的说法）：读代码核实，不默认它成立。

对原话的任何疑问（前提不成立、照做达不到目标、有更好的路），只能写成交给用户的问题，不能据此扩大或改变改动。用户回复之前，一律按原话执行。改动范围始终由 `scope.txt` 和停下条件 2 约束，不因为怀疑原话而放宽。

## 运行目录

每个任务一个运行目录，放在仓库外，避免进 PR：

```
~/.vibe-runs/<仓库名>/<YYYYMMDD>-<任务简称>/
  requirement.md      需求单（模板：templates/requirement.md）
  scope.txt           改动地图：允许改动的路径，一行一个，可用 *（* 跨目录匹配）
  base                起点 commit；branch 是开工时所在的分支
  untracked-at-start  开工时已存在的未跟踪文件及其 sha1；内容没变的不算本次改动
  plan.md             方案；plan-review-<轮次>.snapshot.md 是每轮方案评审时的方案快照
  checks.log          检查命令的原始输出，只能由 scripts/run_check.sh 写入
  closed.md           已结案清单：每条评审意见的判定（采纳 / 驳回 / 作废 / 无法核实 + 证据）
  review-note.md      用户对评审方的追加要求（用户原话），有就附在每轮评审消息里
  review-<阶段>-<轮次>.md        评审原文（计入轮次）；同名 .reviewer 记录这一轮实际用的评审方
  review-<阶段>-<轮次>.failed.md 无效的评审输出（不计入轮次）；.stderr.log 是评审过程日志
  review-external-<n>.md         用户贴来的外来评审原文
  diff-code-<轮次>.patch         这一轮交给评审方的 diff
  pr.md               PR 标题和描述
```

下文 `<SKILL>` 指本技能目录的绝对路径，`<RUN>` 指运行目录的绝对路径。执行命令时替换成实际路径（很多工具的 shell 变量不会在命令之间保留，不要依赖 `RUN=...` 这类变量）。

## 开工准备

只在要改代码时做：完整流程在最开始做，执行入口在开始时做。只读的入口不做。运行目录里已有 `base`（之前已经开过工）时整段跳过，切到 `<RUN>/branch` 记录的功能分支继续。

- 检查工作区：已跟踪文件有未提交改动时停下问用户。
- 同步最新的基准分支（用户指定了就用用户的；否则用 `origin/HEAD` 指向的默认分支；没有远端就用本地默认分支），从它切功能分支。
- 建运行目录（已有就沿用），然后记录起点：

  ```bash
  mkdir -p <RUN>
  bash <SKILL>/scripts/check_scope.sh --init <RUN>
  ```

## 阶段

### 0. 接需求，写需求单

- 按 `templates/requirement.md` 写 `requirement.md`。用户原话**逐字复制**，现在就写，后面上下文压缩后原话会丢。原话指向上文（"就按你的思路来"）时，把被指向的那段结论也原样摘进来，标明是谁说的。
- 按上文「用户原话怎么用」给原话逐句归类，拿不准的归为「决定」。每条「事实判断」都读代码核实，结果写进「前提核实」；有不成立的，按停下条件 6 处理。
- 用户要求维护任务基线时（需求要多轮讨论、怕上下文压缩丢信息），按 `references/task-baseline.md` 在仓库根目录建并维护 `BASELINE_<任务简称>.md`；用户没要求就不建。
- 仓库根目录有 `BASELINE_*.md` 时：只照抄其中已确认的内容——「当前有效方案」条目（注明 S 编号）、「不可变约束」、「初始目标」里的任务目标和标为已确认的本阶段成功标准（注明章节名）；未确认的成功标准、「待确认项」「参考信息」不当作需求。它和对话里用户的话冲突时，停下问用户。
- 判定改动规模，写进需求单（阈值暂定，跑几次后再调）：预计实际改动的文件数超过 3 个，或改动涉及接口、数据结构、权限，算大改；其他算小改。

通过标准：每条成功标准都能对应到一条「决定」、已确认决定或 BASELINE 已确认条目；每条「事实判断」都有核实结果。

### 1. 定位（完整流程和出方案入口只在大改时做）

只读。找到相关代码路径，结论写进 `requirement.md` 的「已知事实」，每条带文件:行号，推断标 [推断]。

### 2. 方案

写 `plan.md`：

- **候选路线（只有大改）**：先列 1-3 条在修复机制或架构落点上真正不同的路线（写法、参数不同算同一条）。每条写：消除的是根因还是触发条件；拿什么换什么；依托项目里哪个现有机制（文件:符号名）；用户会看到的行为。先比较用户会看到的行为：不同路线行为不同，就停下问用户选（停下条件 1），不要自己先选；行为相同，再选一条并写明理由。只有一条合理路线就只写一条，并说明为什么没有第二条。
- **用户指定了做法时**（大改小改都适用）：把它当作候选路线之一，和你想到的路线放在一起比较，不因为是用户提的就默认它对，也不无视它。另一条路明显更好、而且会让用户看到不同的行为或需要改变改动范围时，按停下条件 6 问用户；差别用户看不到（写法、内部实现）时，按用户的做法写，在汇报里用一句话说明另一条路。
- 读了哪些文件；每个文件的 diff（带上下文）、每处标 (a)/(b)/(c)、(c) 移进「额外发现」；对代码现状的描述标 [已读确认] 或 [推断]；验收用例怎么测；未修改声明。未读过的文件不能出现在 diff 里。

写完方案后写 `scope.txt`，和方案 diff 涉及的文件一致。测试文件也算改动，要列进去。尽量列具体文件；只有新建文件且位置确定时才用 `目录/*`。

### 3. 方案评审（独立评审，1 轮，必要时加 1 轮定向复审）

```bash
bash <SKILL>/scripts/review.sh plan <RUN>
```

按下文「处理评审意见」逐条判定，写进 `closed.md`，改 `plan.md`。

只有第 1 轮里有 [核心] 问题被你采纳、方案因此改过时，再跑一次同样的命令做定向复审：评审方只看方案改过的部分，以及采纳的问题有没有改对。没有采纳 [核心] 就不复审，直接进下一阶段。复审后剩下的问题由代码评审兜底。

### 4. 先写验收测试，确认它失败

项目有测试框架时，先写能证明需求的测试，用 `run_check.sh` 跑一次，`checks.log` 里要看到它失败。没有测试框架或需求只能在页面上验证时，在 `plan.md` 里写清实测步骤和预期结果，按阶段 9 处理；不为此新建测试框架。

### 5. 执行

单写者，按 `plan.md` 应用 diff。diff 对不上当前代码或 [推断] 不成立时，按 `references/execution-rules.md` 的冲突处理办。

### 6. 命令检查

```bash
bash <SKILL>/scripts/run_check.sh <RUN> -- <测试命令>
bash <SKILL>/scripts/run_check.sh <RUN> -- <lint / typecheck 命令>
bash <SKILL>/scripts/run_check.sh <RUN> -- bash <SKILL>/scripts/check_scope.sh <RUN>
```

通过标准：验收测试从失败变为通过；原有测试没有新增失败；`check_scope.sh` 退出码为 0。超出改动地图就按停下条件 2 停下，由用户决定是否扩大范围；用户同意后才改 `scope.txt`，并在 `requirement.md` 变更记录里写明用户的原话。不要自己扩大 `scope.txt` 让检查通过。

### 7. fork 自检（1 轮）

用当前工具的 fork 能力（继承本对话上下文的子 agent），把 `prompts/self-check.md` 的全文原样交给它，并告诉它运行目录的路径。工具没有 fork 能力时，你自己按那份清单做一遍。自检的每条意见都打开代码核对，判定写进 `closed.md`；成立的修掉，修完回到阶段 6（自检入口只报告，不修）。

### 8. 独立评审（最多 2 轮）

评审前先把改动 commit 到功能分支（脚本要求已跟踪文件没有未提交改动、没有新的未跟踪文件，用 commit 记录每轮的起点）。

```bash
bash <SKILL>/scripts/review.sh code <RUN>
```

结论为通过、且没有你判定为采纳的 [核心] 问题，就结束评审。否则修完采纳项、commit，再跑第 2 轮。第 2 轮后仍有未解决的 [核心] 问题，原样写进最终汇报和 `pr.md`，继续准备 PR。

### 9. 实测（默认不做，由用户决定）

只有用户要求实测时才做（例如需求里写了"用浏览器实测一下"）：用当前可用的浏览器自动化工具或技能按验收用例操作一遍，结果写进最终汇报：操作、看到的现象、是否符合预期。用户没要求、而验收用例里有只能实测的项时，不做实测，在最终汇报里列出这些用例的操作步骤和预期结果，由用户决定要不要测。

### 10. 准备 PR，到此停下

改动 commit 在本地功能分支上，不 push、不创建 PR，推送和创建由用户自己做。commit message 用英文，不加任何 AI 署名（包括 Co-Authored-By）。PR 标题和描述写进 `<RUN>/pr.md`：解决了什么、验收方式（含未做的实测项）、未解决的评审问题。

## 评审代码的准备

评审不是在本流程里写的改动（用户自己或别人写的分支、commit 范围）时，先做这些：

- 待评审的版本要是当前检出的 HEAD。不是时：已跟踪文件没有未提交改动就切过去，评审结束后切回原来的分支，汇报里写明；有未提交改动就停下问用户。
- 待评审的改动还有没 commit 的部分时，停下问用户：评审只看已 commit 的改动，这些改动由用户自己 commit。
- 建运行目录，记录起点。用户给了 commit 范围就用范围的起点，否则用基准分支：

  ```bash
  mkdir -p <RUN>
  bash <SKILL>/scripts/check_scope.sh --init <RUN> <起点 commit 或基准分支>
  ```

  脚本把起点和当前 HEAD 的分叉点写进 `base`。
- 写 `requirement.md`：用户原话，加上 PR 描述和 commit message（`git log <base>..HEAD`）原样摘录，注明来源，再按阶段 0 归类、核实。都没有需求说明时只写用户原话，评审方会跳过核对需求的那一项。
- 项目有测试命令时，用 `run_check.sh` 跑一次测试。
- 没有 `plan.md`、`scope.txt` 不用补；脚本会告诉评审方缺哪些材料，评审方跳过依赖它们的评审项。

## 评审方

- `review.sh` 按顺序找评审方：环境变量 `DEV_FLOW_REVIEWERS` 列出的名字（默认 `codex claude dsh`），跳过不在 PATH 里的。某个评审方退出码非 0、输出为空或输出里没有有效结论行时，换下一个，并在输出和 `.reviewer` 文件里写明这一轮实际用的是哪个。
  - `codex`：`codex exec -s read-only`（只读沙箱）。
  - `claude`：`claude -p --permission-mode plan`（只读模式）。
  - `dsh`：`dsh --profile <配置名>`，配置名用环境变量 `DEV_FLOW_DSH_PROFILE`，默认 `headless`。
- 用户指定其他评审命令时，设环境变量 `DEV_FLOW_REVIEWER`（例如 `DEV_FLOW_REVIEWER="claude -p"`）；只接受不带引号的简单命令。指定后只用它，失败不换别的。
- 评审 Prompt 固定用 `prompts/` 里的文件，由脚本原样发出，你不改写、不另写。用户对评审方有追加要求（例如"这次重点看并发"）时，把用户原话原样写进 `<RUN>/review-note.md`，脚本会附在每轮评审消息末尾。
- 每一轮评审都是新开的评审进程，不续接上一轮的会话。评审方知道的一切都来自运行目录里的文件：
  - 方案评审第 1 轮：需求单、方案、改动地图、`closed.md`（如有）。
  - 方案评审第 2 轮（定向复审）：另外读第 1 轮评审原文、第 1 轮时的方案快照和更新后的 `closed.md`，只看改过的部分。
  - 代码评审第 1 轮：需求单、改动地图、`checks.log`、完整 diff、开工前的未跟踪文件清单、`closed.md`；先按需求单和 diff 自己判断，再读 `plan.md` 了解意图、核对方案里的现状描述。其中缺的文件，脚本会在评审消息里列出。
  - 代码评审第 2 轮：在第 1 轮基础上，另外读第 1 轮之后的增量 diff、上一轮评审原文和更新后的 `closed.md`。
  - 所以 `closed.md` 里的驳回理由要写全证据，评审方只能从这里知道你为什么驳回。

`review.sh` 的退出码：

- 3：这一阶段的评审已达轮数上限，剩余问题写进汇报，继续往下走。
- 4：评审方改了已跟踪文件或运行目录，这一轮作废；把改动恢复后重跑一次，再出现就停下问用户。
- 5：没有可用的评审方（列出的评审方都不在 PATH 或都失败）。按停下条件 5 停下，不要跳过评审继续往下走。
- 脚本列出"评审期间出现了新的未跟踪文件"时，多半是评审方跑测试的产物，确认不是你的改动后删除。

## 处理评审意见

适用于方案评审和独立评审的每一条意见；fork 自检的意见不走作废规则，逐条打开代码核对即可。

- **作废**：缺位置（文件:行号，或需求单 / 方案里的具体条目），或缺具体触发场景（也没有附可失败的测试）的。作废不需要回复评审方。
- **采纳**：自己打开代码核对后成立的。只改这条意见涉及的地方，不借机扩大 diff。
- **驳回**：核对后不成立的，必须附证据（文件:行号 + 观察值，或命令输出）；只有推理不能驳回。
- 每条写进 `closed.md`：`<阶段>-<轮次>-<编号> | 采纳/驳回/作废 | 级别 | 一句话 | 证据`（阶段写 plan / self / code / external）。
- 评审方的意见是待核实的主张，不因为它说得肯定就采纳；评审结论写"通过"但问题清单里有 [核心]，照样逐条判定。
- 评审输出的「需要用户决定」里列出的点，不论评审结论是否通过，都按下文「停下问用户的条件」判断要不要停。

### 处理外来评审意见

用户贴来别人写的或其他工具出的评审时：

- 原样存成 `<RUN>/review-external-<n>.md`。和某个已有运行目录相关就放进那里；没有就新建运行目录，按阶段 0 写需求单（需求单写的是被评审的那件事的需求）。
- 逐条打开代码核对。外来评审的格式不一定合规，不按作废规则处理：缺位置的自己去找；找不到、或核对需要的证据拿不到的，判为「无法核实」，写明缺什么证据。能通过读代码判断的，不许判「无法核实」。
- 先查 `closed.md`：同一个问题以前已经结过案的，写明当时的结论和编号，没有新证据不重新判定。
- 判定写进 `closed.md`（阶段写 external，判定为采纳 / 驳回 / 无法核实）。
- 汇报：先写采纳的意见会让方案或代码怎么变（保留什么、新增什么、删掉什么）；再逐条写判定和证据；最后把需要用户决定的点按「停下的方式」列出。不改代码或方案，用户确认后再按对应入口改。

## 停下问用户的条件

只有下面六种情况停下：

1. 需求有歧义：用户原话能读出两种意思，或几条候选路线会让用户看到不同的行为，或一句话归为「决定」还是「比方 / 理由」会导致不同的做法。
2. 要修某个问题，必须改改动地图外的文件，或改变接口、数据、权限、原有行为。
3. 僵持：你带证据驳回了一条 [核心]，评审方下一轮带新证据坚持。
4. 同一个问题修了两次还在。
5. 没有可用的评审方（`review.sh` 退出码 5）。
6. 原话本身可能有问题，而且有证据：用户的事实判断和代码不符（附文件:行号）；照原话做达不到原话自己想解决的问题（附具体场景）；用户指定的做法之外有明显更好的路，而且会让用户看到不同的行为或需要改变改动范围。尽量在写代码之前（阶段 0-3）发现并提出。

其余分歧（[边缘]、[凑数]、两种写法都能通过验收的技术选择）你自己决定，理由写进 `closed.md`，汇报里列出。

停下的方式：先把当前这一轮所有意见判定完，不依赖用户决定的采纳项先修完，然后一次列出需要决定的点（最多 3 个），每个点写清选项、实际差别、你的建议。阶段 0-3 发现的问题尽量攒到方案评审结束后一起问；只有前提不成立让方案无从下手时，才在写方案前单独问。用户的回答写进需求单的「已确认的决定」，原样引用。有发送通知的技能可用时（例如飞书、Slack 通知），按它的"任务未完成"格式发一条通知。

## 汇报

只做一段时，只汇报这一段：产出了哪些文件（路径）、结论、需要用户决定的点、要继续时可以怎么说。走完整流程或执行入口时，最终汇报写：

- 功能分支名；完整流程还要写 `<RUN>/pr.md` 路径，以及用户自己推送和创建 PR 要运行的命令；改了什么（`git diff --stat`）
- 验证：引用 `checks.log` 里的命令和结果；做了实测时写实测结果，没做时列出待实测的用例
- 评审记录：每轮评审用的评审方和结论，采纳 / 驳回 / 作废各几条，驳回的理由各一句
- 未解决的问题、偏离本技能的地方及原因
- 按原话执行、但你有不同看法的地方（每处一句话：原话是什么、你的看法、依据）
- 运行目录路径
