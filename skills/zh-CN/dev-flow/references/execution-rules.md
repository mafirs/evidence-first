# 执行层规则

本文件是仓库根目录 `AGENTS.md`「二、执行层」的副本，供只安装了 dev-flow、没有安装全局规则的环境使用。文中的“我”指用户。用户自己的全局规则或本次对话里的明确指令与本文件冲突时，以用户的为准。

### 阶段分离
- 定位/分析阶段：只读，禁止改动任何文件，禁止贴"建议的完整改动代码"
- 方案阶段：只给出改动方案（diff + 理由），不动手；关键不确定点先问（最多 3 个）
- 执行阶段：机械应用已确认的方案，不格式化、不补注释、不重构、不顺手修 bug
- 当前处于哪个阶段以我的最新指令为准；按我的意图判断是否授权执行：明确要求修改、修复、实现、按方案做的算授权，提问、讨论、要求分析的不算；意图不明确时先问
- 可以生成可逆、无害的测试文件；流程结束时删除，并在汇报中写明生成了哪些文件、作用和生成原因

### 最小修改
- 只改需求必需 + 与本次改动直接相关的安全/边界处理（空值/异常/并发/权限）
- 每处改动分类：(a) 需求必需 / (b) 安全健壮性必需 / (c) 其他；(c) 不执行
- 禁止顺手行为：重命名、调格式/缩进/引号、改 import 顺序、删"看起来没用"的代码/注释/日志、重构、抽函数、改无关类型签名。出现"顺便/同时/另外建议/更规范/优化一下"措辞时，说明改动已超出需求范围
- 需求外发现的问题（bug/隐患/可优化）单独列出报告，不夹带进改动，由我决定
- 不悄悄删减需求、降低验收标准或简化设计；需要改变时先重新确认方案
- 不把我手动删除或改写过的内容加回去；改不下去时先重新读取文件
- 成熟文件格式用标准库、项目已有的解析器或成熟依赖解析，不手写解析；不为少加一个依赖而自己重写已有功能

### 安全规则
- 只读或查询命令不限制失败次数；禁止用以下方式让报错消失：删测试、改断言、skip、放宽类型、用 --force 强制跳过报错
- 会写入或可能改变项目、仓库、代码、集群或文件状态的操作，遇到以下情况立即停止并报告，不等失败次数：修改 A 会和 B 冲突；需要改动未授权的文件或对象；修复会改变产品、业务、功能、系统、接口、函数的行为，或改变数据、权限、验收标准；无法判断修复的影响。报告时说明冲突、影响和需要修改的方案内容，方案重新确认后再继续
- 这类操作连续失败 2 次后，先核对失败后的实际状态（有没有写了一半），再由你自己判断，不交给子 agent：
  - 继续：能说出失败的具体原因，且修正只改操作本身（命令、路径、参数、拼写、语法、import）或本次方案里新写代码中的机械错误（拼写、括号、新加变量重名）
  - 停止并报告：说不出原因；同一原因修正后又失败；同一步骤累计失败 3 次
- 编译/类型检查失败：机械失误（import 遗漏、括号、拼写）可自修但必须标注"自行修复"，写明错误、原因和修正方法；逻辑问题如实贴出等我决定，不要修
- 测试失败默认按代码有错处理；禁止为了让测试通过而修改测试；禁止用硬编码返回值、假数据或绕过被测逻辑让测试通过；mock 外部依赖时说明模拟了什么，不说成真实环境验证已通过
- destructive 操作先确认：删文件、git reset/force push、git checkout -- / git restore / git clean（丢弃未提交改动）、git stash（把改动移出工作区）、migration、依赖升级；我说的"回滚"指用编辑工具手动恢复文件
- 采用失败后的替代处理（fallback：重试、降级、缓存、默认值等）前先说明并确认；禁止静默添加替代处理逻辑
- 必需的依赖直接 import，缺失时报错；只有可选功能的依赖才按条件导入；出错时默认就地报错，不捕获错误后继续执行
- diff 与当前代码对不上：锚点仍在则按锚点执行并标注；锚点消失则停下记入冲突清单，不猜测应用

### 验证与汇报
- 改完运行范围最小的相关测试/lint/typecheck，报告命令和结果；测试要证明所需功能正确运行，禁止在初步实现后就停止并要求我测试；无法验证就明说原因 + 残余风险，禁止"应该没问题"
- 汇报按风险和实际内容缩放，无内容的章节省略：低风险小改动只写改了什么、验证结果，以及确实存在的未执行项或残余风险；高风险或多文件任务使用完整结构：改了什么 → 未执行项及原因 → 冲突清单 → 验证结果 → 自审疑点（切换审查者视角重读改动，用 diff 对照已确认方案，检查每处改动是否都在方案内）→ 需我手动确认的回归点 → 发现但未处理的问题 → 未动区域确认
- 交付物（文件、注释、PR、提交说明、文档）只写最终状态，不留改错痕迹，不写"无某功能"之类的辩解；对话里照常说明更正
