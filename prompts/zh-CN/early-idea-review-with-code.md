## 本轮评审四件事

1. 对题度
该 agent 的思路解决的是不是动作 0 里复述的原始诉求？有没有偏题、漏掉原问题、或扩张到原问题之外？
特别注意：思路有没有绕开原问题去做更大的事。

2. 实读代码 vs 该 agent 自陈的对比
逐条列出该 agent 在对话里提到的关键工程前提（数据形状、已有逻辑、调用关系、文件结构等），每条标三选一：
- [对话+实读一致]：该 agent 说的和我读到的代码一致
- [对话+实读冲突]：该 agent 说的和实际代码不符——具体冲突点写明，给出文件:行号
- [agent 没说我读后补充]：该 agent 完全没提、但实际跟思路相关的代码——给出文件:行号和为什么相关

[对话+实读冲突] 和 [agent 没说我读后补充] 这两类是这一阶段最高价值的产出，重点找。

3. 是否有更小的路
不重新设计、只修原 bug 直接成因，能不能解决？
如果说"有"，必须给出具体到文件:行号的修复点。给不出来就写"无"。

4. 路线比较：是否有更适合当前项目的思路
读完代码后，判断该 agent 当前思路是不是当前项目里最合适的路线。
这里不是让你自由提出优化建议，而是只比较"解决同一个原始诉求"的不同路线。

你只能提出同时满足以下条件的替代路线：
- 解决的仍是动作 0 复述的原始诉求，不扩张问题域
- 不是具体实现方案，不写代码，不展开 SQL/API/边界条件
- 必须基于实际读到的代码，而不是通用最佳实践
- 必须能指出该 agent 当前路线为什么不如它适合本项目
- 必须引用项目已有代码模式、调用关系或架构惯例，并给出文件:行号
- 不能只是"更优雅 / 更严谨 / 更完整"，而必须是"在这个项目里更一致 / 更少改动 / 更贴近既有入口 / 更符合已有职责边界"

如果该 agent 当前思路已经是合理路线，路线判断写"当前路线已合适"，其余字段写"无"。
如果只有更小修法，路线判断写"仅有更小修法"，其余字段写"见更小的路"，不重复展开。
如果选"无法判断"，必须在"缺少的信息"字段说明缺少哪类信息才能做出判断，不允许留空。

格式：

## 产品语义闸 — 强制

## 凑数标签 — 强制

你列出的每一条问题，末尾必须标三选一：
- [核心] 我有把握这是真问题，不解决会真出事
- [边缘] 理论成立，但我不确定现实中会不会真触发
- [凑数] 实话——如果不是因为要列出问题，我不会主动提

[凑数] 的典型特征：
- 理论成立但发生需要"恰好+恰好+恰好"几个条件叠加
- 只在反常使用路径下才触发
- 属于当前系统既有取舍而本思路没加重
- 读完代码后发现实际代码就是按你担心的方式实现的（问题不存在）

如果你写完一条的论证里出现"如果用户……如果系统……如果同时……"这种连环假设，多半是[凑数]。

[凑数] 标签可以用，没有惩罚。比硬装[核心]更可信。
我不会因为你标[凑数]扣分，但会因为你把[凑数]伪装成[核心]扣分。

## 禁止行为

- 不要列只在恶意/反常使用路径下才成立的问题
