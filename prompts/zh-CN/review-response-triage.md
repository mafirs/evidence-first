## 你的任务

**不要顺着对方的话展开**。把这份评审转化成下一版正式方案前的决策清单。

## 输出顺序 — 强制

1. 思路变化总结（先输出）
2. 逐条回应（证据/依据）
3. 归档项（一句话带过的低价值条目）

注意：执行顺序是先完成复核，再生成总结；输出顺序仍然必须先展示"思路变化总结"。

## 一、思路变化总结 — 必须先输出

逐项填写，不允许用"整体符合预期""基本不变"这类话概括。

1. 最初思路保留了什么？
2. 经过评审后，思路新增了什么？
3. 经过评审后，思路删掉或降级了什么？
4. 对方有没有提出你之前没考虑到、且确实成立的问题？
   有 → 列出；没有 → 写"无"并说明为什么
5. 对方有没有钻牛角尖？
   有 → 指出是哪几条，为什么不影响当前思路
6. 有没有需要用户拍板的产品语义或取舍？
   格式：[决策点] — 选项 A vs 选项 B — 我的倾向是 X，需要用户确认+倾向原因（说人话，不堆术语不类比，不比喻）
   没有 → 写"无"
7. 有没有如果不改会影响真正上线、或给后续方案挖坑的点？
   有 → 列出 文件:行号 或 模块名；没有 → 写"无"并说明

## 二、逐条回应

动作 1 — 复核对方的关键批评

必须复核以下条目：
- 对方标为 [核心] 的问题
- 对方标为 [对话+实读冲突] 的工程前提
- 对方标为 [agent 没说我读后补充] 且影响当前思路的代码事实
- 对方提到的"更小的路"
- 对方路线比较结论为"有更适合路线"时，该路线及其依据
- 对方提到的产品语义/用户拍板项

[边缘] 条目若可能改变正式方案也要复核；否则进归档项。
[凑数] 默认归档，除非你认为对方低估了它。

对以上每条判断：属实 / 部分属实 / 不属实 / 无法判断

规则：
- 无论判断为"属实/部分属实/不属实"，都必须给出依据：代码证据（文件:行号）、对话证据或产品语义证据
- 没有打开对应文件就不能得出"不属实"结论，此时写"无法判断"
- 选择"无法判断"时，必须说明缺少什么证据；能通过读代码或对话上下文判断的，不允许写"无法判断"
- 每条都必须回溯本次对话历史，确认此前是否已讨论并结过案；已结案的，写明当时的结论，不得当作新问题重新论证
- 若必须复核的条目分属至少两个互不依赖的证据域，可并发分派只读子Agent，每个子Agent必须获得相同的原始诉求和产品语义，只返回被核验主张、角色约定的真伪状态、决定性证据、冲突和缺失证据，不决定是否采纳
- 你必须合并重复项、处理证据冲突并重新打开决定性文件，再统一给出复核结论、处理结论和思路变化总结；不得直接拼接子 Agent 输出

动作 2 — 每条格式

对应对方第 X 条：[简述]
- 所属层级：代码架构层 / 功能层 / 用户体验层
- 复核结论：属实 / 部分属实 / 不属实 / 无法判断
- 是否已讨论过：是（此前结论：___）/ 否
- 处理结论：必须改思路 / 方案阶段展开 / 暂不处理 /
            对方判断不成立 / 需要用户拍板
- 不修的后果：[一句话，我会看到什么变化。不堆术语，不用比喻。
              复核结论为"不属实"或该条为 [凑数] 时写"无"]
- 理由：[限 3 句话]

压缩规则：
- 上述检测与自查对全部条目逐条执行，不得抽样；压缩只作用于输出
- 逐条回应最多保留 6 条；每条理由最多 3 句。其余进归档项
- 处理结论为"必须改思路"且理由显而易见 → 理由压缩到 1 句
- 多条重复批评合并，保留原编号
- [凑数] / [边缘] 且不影响方案的条目 → 直接进归档项

## 三、归档项

每条一句话：
第 X 条 — [凑数 / 不属实 / 已覆盖 / 此前已讨论] — [一句话说明为什么不处理]

## 禁止行为

- 禁止写"加测试/加日志/加注释/更严谨/注意边界"等无具体指向的话
- 禁止用比喻、类比、拟人说明后果，只描述实际会发生的现象
- 禁止给具体代码实现
- 禁止预演尚未确定的实现细节
- 禁止在未打开文件的情况下对代码现状做确定性表述
